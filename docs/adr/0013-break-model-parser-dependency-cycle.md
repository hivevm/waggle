# ADR-0013: Break the `model` ↔ `parser` dependency cycle

- **Amended (2026-09-19):** decision 1 originally moved `Token` to a hand-written
  `org.hivevm.core.Token` and suppressed the generated one through a new `TOKEN_CLASS` option. That

## Context

The [specification](../SPECIFICATION.md) §4 stages the pipeline so that **stages 1–4 are a
language-independent front end** and stage 5 is the target-specific back end.
[ADR-0004](0004-multi-target-code-generation.md) reinforces this: the back ends render a **shared,
language-independent model**. The model (`org.hivevm.cc.model`) is therefore meant to be the stable,
foundational artifact of the front end — depended upon, depending on little.

The implementation contradicts this: `model` and `parser` form a **package cycle**.

- `org.hivevm.cc.parser` → `org.hivevm.cc.model`: **11** import edges. This is the natural direction
  — stage 2 parses the grammar and *builds* the model.
- `org.hivevm.cc.model` → `org.hivevm.cc.parser`: **11** import edges across **10** model classes.
  This is the edge that should not exist. It breaks down into five distinct couplings:

  | Coupled `parser` type | Model files | What the model actually needs |
  | --- | --- | --- |
  | `Token` | 7 (`Production`, `Action`, `Lookahead`, `NonTerminal`, `RExpression`, `TokenProduction`, transitively `RegExprSpec`) | The **full token contract via public fields**. Two uses: (a) location markers (`beginLine`/`beginColumn`) for error reporting, and (b) **verbatim token chains** — `List<Token>` for embedded actions, return types, parameter lists and throws clauses that the back ends re-emit into generated source by walking `image`, `next` and `specialToken` (37 `.next`, 25 `.image`, 14 `.specialToken` reads across the generators). A position-only value type does **not** cover use (b). |
  | `RegExprSpec` | `TokenProduction` | Nothing external — `RegExprSpec` is *itself* a model concept ("entries in the `respecs` vector of `TokenProduction`") that merely lives in the wrong package; it holds `RExpression`/`Action` (model) references. |
  | `ParserDescriptor` | `NodeScope` | `ParserDescriptor` *implements* the model interface `NodeDescriptor`; the model should not import its own implementor. |
  | `Options` | `NodeDescriptor` | A narrow config view. `Options` already `extends org.hivevm.core.Environment`; `NodeDescriptor.getNodeClass` needs only an option lookup. |
  | `JavaCCErrors` | `CharacterRange` | To report one validation error (invalid character range). `JavaCCErrors` is the process-global static error sink. |

Three facts sharpen the picture:

1. **`Token` is part of the generated parser.** It is copied from the template resource
   `src/main/resources/templates/java/Token.java` into every generated parser — including HiveVM CC's
   own self-hosted parser at `src/main/generated/org/hivevm/cc/parser/Token.java`
   ([ADR-0009](0009-self-hosting-bootstrap.md)). The generated lexer constructs it, the generated
   parser links `next`/`specialToken` chains through it, and the grammar actions hand it to the
   model. It is the runtime contract of the generated parser, not an independent type.
2. **The self-hosted parser is generated by the previous release.** `./gradlew generateParser` runs
   the **published** plugin pinned in `build.gradle`, not the generator in the working tree. The
   self-hosted grammars (`JavaCC.jj`, `JJTree.jj`) can therefore only rely on what that release
   generates. Anything that changes what is emitted for the self-parser — for example, not emitting
   `Token` — cannot be introduced and used in the same release. The first version of decision 1 did
   exactly that: it added a `TOKEN_CLASS` option to import `org.hivevm.core.Token` instead of
   emitting `Token`; the published plugin 1.0.11 ignored the unknown option
   (`Bad option name "TOKEN_CLASS"`), emitted `parser.Token`, and the regenerated parser failed to
   compile against the `core.Token`-based code (77 errors).
3. **A neutral base layer already exists.** `org.hivevm.core` holds `Environment` and `Version` and
   is depended upon by `parser` but **not yet** by `model`. It is the natural home for shared
   abstractions.

Consequences of the cycle today: the model cannot be compiled, unit-tested, or reused without
dragging in the parser layer and its static error sink; the front-end/back-end boundary the
specification mandates cannot be enforced by a package rule; and the "enforceable layering" that
[ADR-0012](0012-lexer-owns-dfa-construction.md) just made possible on the lexer/generator edge is
still blocked on this one.

**State of the art (researched).** This is the textbook violation of Robert C. Martin's **Acyclic
Dependencies Principle** — a component dependency graph must be a DAG. The three established
techniques for breaking such a cycle are (1) **dependency inversion** (flip one edge behind an
abstraction owned by the depended-upon side), (2) **merge** the two components, and (3) **extract a
shared abstraction** into a third, lower, stable component. SEI CERT `DCL60-J` codifies the same rule
for Java packages. The resolution below applies technique (1) for `JavaCCErrors` and simple
**relocation to the correct layer** for the concepts that are merely misplaced. For `Token`,
upstream JavaCC (7.x), from which HiveVM CC is forked ([ADR-0003](0003-fork-javacc-as-baseline.md)),
keeps its grammar model (`NormalProduction`, `Action`, `Expansion`, …) on the `Token` generated from
its own `JavaCC.jj`; self-hosting compilers generally treat the bootstrap generator as a fixed
stage-0 and only adopt new generator features in the self-grammar after a release that contains them.

## Decision

We will make **`org.hivevm.cc.model` downward-only**: it may depend on `org.hivevm.core`, the JDK,
and the generated `org.hivevm.cc.parser.Token`, and **must not import anything else from
`org.hivevm.cc.parser`** (nor any later stage). The reverse edge (`parser` → `model`) stays; stage 2
continues to build the model. Concretely:

1. **Token — keep the generated class.** The model needs the full token contract (image, kind,
   `next`, `specialToken`, positions) via public-field access, both for location markers and for the
   verbatim token chains the back ends re-emit; a position-only value type is insufficient (see
   Context). Because `Token` is part of the generated parser and the self-hosted parser is generated
   by the previous release, the model, semantic, generator and parser-side code use the generated
   `org.hivevm.cc.parser.Token`, as every other generated parser does. `org.hivevm.cc.parser.Token`
   is the **single permitted** `model → parser` import. There is no `TOKEN_CLASS` option and no
   hand-written `org.hivevm.core.Token`.

2. **Relocate misplaced model concepts.** Move `RegExprSpec` into `org.hivevm.cc.model` — it is a
   model concept. Move or invert `ParserDescriptor` so the model no longer imports its own
   implementor (`NodeScope` depends on the `NodeDescriptor` abstraction it already owns; the concrete
   `ParserDescriptor` lives on the parser side or is folded into the model as data).

3. **Depend on the stable config abstraction.** `NodeDescriptor` (and any other model use of
   `parser.Options`) references `org.hivevm.core.Environment` (or a narrow config interface declared
   in `core`) rather than `parser.Options`. `Options` already extends `Environment`, so this narrows,
   not widens, the contract.

4. **Invert the error edge.** The model must not import the global static `JavaCCErrors`. The
   `CharacterRange` validation either (a) reports through an error-reporter abstraction supplied by
   the caller, or (b) moves to the semantic stage (§3) where such cross-checks belong. Either way the
   model reports *up through an abstraction*, never down into a concrete sink. (Retiring the
   process-global nature of `JavaCCErrors` itself is broader than this ADR and remains separate.)

5. **Enforce it.** Add an automated package-dependency check asserting `model` depends only on the
   JDK, `core`, itself and `org.hivevm.cc.parser.Token`, so the boundary cannot silently regress. A
   test also asserts that generating the self-hosted grammars emits `Token.java`.

## Consequences

- **The model is close to what the specification says it is:** apart from the generated `Token`,
  it is a language-independent artifact that no longer depends on the parser layer, its options or
  its static error sink — serving SPEC §4 and ADR-0004.
- **One edge of the cycle remains, deliberately.** The model cannot be compiled without the
  generated `Token`. This is the price of keeping the bootstrap working with the published plugin;
  the package rule makes sure it stays the only one.
- **Enforceable layering.** With the package rule in place, the front-end boundary is guarded
  mechanically, completing the direction ADR-0012 set on the lexer/generator edge.
- **Bootstrap rule.** A change to what the generator emits for the self-grammar must land in a
  published release before `JavaCC.jj`/`JJTree.jj` may depend on it.
- **Users' parsers are unaffected**; they always emit their own self-contained `Token`.
- **Cost and risk.** The relocations are mechanical. The `JavaCCErrors` inversion is the subtlest
  part and partially overlaps a larger global-state cleanup; it may be landed as its own step. As
  with ADR-0012, this is best done under a safety net — byte-identical bootstrap regeneration plus the
  Java/C++/Rust generate-and-compile tests — and split into reviewable steps.
- **Follow-up enabled.** A clean `model` is the precondition for later addressing the remaining
  global-state residue (`JavaCCErrors`, `NodeScope` static collections) and for any future extraction
  of the front end into its own module.

## Alternatives considered

- **Merge `model` and `parser` into one package.** Rejected: the two have distinct responsibilities
  and the SPEC's staged pipeline treats them as separate stages; merging would erase a boundary the
  specification wants sharper, not gone, and their cohesion does not justify it (ADP technique 2 fits
  only tightly-cohesive pairs).
- **Position-only value type, `Token` adapted at the stage-2 boundary.** Rejected: the model does
  not hold `Token` only for positions — it holds verbatim `List<Token>` chains that the back ends
  re-serialise into generated source by walking `next`/`specialToken` via public fields. A position
  value cannot carry that, and a boundary adapter cannot wrap public-field access.
- **Hand-written `org.hivevm.core.Token` plus a `TOKEN_CLASS` option.** Implemented first and
  reverted (see the amendment above): the published plugin that regenerates the self-hosted parser
  does not know the option and emits its own `Token`, so the build breaks.
- **Keep `core.Token` and release first (two-stage bootstrap).** Publish a plugin version containing
  `TOKEN_CLASS`, then bump `build.gradle` to it. Rejected: it makes the build depend on a release
  step for an internal refactoring, and still requires a working stage-0 parser for the interim; the
  cycle it removes is a single, stable class.
- **Convert tokens at the parser boundary.** Keep `core.Token` in the model and copy each
  `parser.Token` (including its `next`/`specialToken` chain) when the grammar actions build the model.
  Rejected: every action that passes tokens or token lists would need a conversion call, chain
  identity has to be preserved across copies, and it adds a second, parallel token type.
- **Generated `Token` extends `core.Token`.** Rejected: needs a new generator option (same bootstrap
  problem), and the inherited `next`/`specialToken` fields would be typed as `core.Token`, forcing
  casts throughout the generated parser.
- **Leave the cycle and suppress the warning.** Rejected: it violates SPEC §4 and ADR-0004, keeps the
  model un-testable in isolation, and blocks the package-rule enforcement that ADR-0012's layering
  work was meant to make possible.
- **A shared static utility both packages call (for the error sink).** Rejected for the same reason
  ADR-0012 rejected it: it treats the symptom (the import) without inverting the dependency, and
  keeps the model reaching toward a concrete, process-global sink instead of reporting up through an
  abstraction.
