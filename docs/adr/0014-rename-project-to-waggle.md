## Context

The project is published as **HiveVM CC** ("Compiler-Compiler"). "CC" is generic: it is the suffix
of JavaCC, of the C compiler driver `cc`, and of the `.cc` C++ source extension this very project
emits; it is not searchable and does not identify the tool. The maintainer has decided to rename the
project to **Waggle** — in the HiveVM naming family (a *waggle dance* is how bees encode and pass on
structured information).

The name "CC" is not only prose. It is baked into interfaces that users and builds depend on:

| Surface | Today | Who depends on it |
| --- | --- | --- |
| Gradle plugin id | `org.hivevm.cc` | every consumer's `plugins { }` block (ADR-0006) |
| Maven coordinates | `org.hivevm:<checkout dir>` — `settings.gradle` sets no `rootProject.name`, so the artifact is named after the directory (`cc` on CI, `workspace` in the Dev Container) | plugin marker resolution |
| Java packages | `org.hivevm.cc.*`, including the SPI file `META-INF/services/org.hivevm.cc.generator.Generator` (ADR-0004) | embedders of the `ParserBuilder` API |
| Brand-carrying types | `HiveCC`, `HiveCCOptions`, `HiveCCVersion`, `HiveCCPlugin` | embedders, the plugin descriptor |
| Grammar file extension | `.jj`, inherited from JavaCC | grammar authors, `build.gradle` files |
| C++ runtime header | `JavaCC.h` with `JAVACC_*` include guards and configuration macros (`JAVACC_CHAR_TYPE`, `JAVACC_STRING_TYPE`, …) | generated C++ code and user code that includes it or overrides the macros |
| Generated-file header, CLI banner | `Generated by HiveVM CC`, `Java Compiler Compiler Version …` | readers of generated code |
| Repository | `github.com/hivevm/cc` | contributors, `vcsUrl`, badges |

Facts that constrain how the rename can be done:

- **Gradle plugin ids cannot be renamed** on the Plugin Portal; a new id is a new plugin. Consumers of
  `org.hivevm.cc` keep resolving the last `cc` release and receive no updates under the new id.
- **The build is self-hosting** ([ADR-0009](0009-self-hosting-bootstrap.md)): `build.gradle` applies
  a *published* release of its own plugin (so far `org.hivevm.cc` 1.0.11) to generate its own parser.
  It can bootstrap from `org.hivevm.waggle` only once a release under that id exists.
- **GitHub keeps redirects** for a renamed repository (web, clone, fetch and push), so the repository
  move does not break existing clones immediately, but the redirect is lost if a new repository ever
  takes the old name.
- **The grammar extension is a convention, not a check.** The driver accepts any extension; it only
  derives the sibling `.lex` file by replacing the extension and treats `.jjt` specially
  ([ADR-0010](0010-unified-grammar-and-actual-surface-syntax.md): `.jjt` is an alias routed through
  the legacy JJTree banner).
- Much internal vocabulary descends from **JavaCC**, not from the "CC" brand: the `JJ*`/`jj*` prefixes
  in generator code and in every generated lexer/parser (`jj_consume_token`, `jjmatchedKind`, …), the
  `JJPARSER_*`/`JJTREE_*` option keys, and classes such as `JavaCCErrors`, `JavaCCData`, `JJDoc`,
  `JJTree*`. Several hundred occurrences, most of them emitted into user code.

## Decision

We will rename the project to **HiveVM Waggle** and change every surface that carries the "CC" brand,
in one change:

1. **Product name.** "HiveVM CC" / "HiveVM Compiler-Compiler" becomes **"HiveVM Waggle"** in the
   README, specification, tutorials, the ADR index, plugin metadata (`displayName`,
   `Implementation-Title`, tags), the Dev Container and CI workflow names, and the VS Code tasks.
2. **Gradle plugin id** `org.hivevm.cc` → **`org.hivevm.waggle`**; the plugin class `HiveCCPlugin` →
   **`WagglePlugin`**. The DSL (`parserProject { task { … } }`) and the `generateParser` task are
   unchanged.
3. **Maven coordinates** are fixed as **`org.hivevm:waggle`** by setting `rootProject.name = 'waggle'`
   in `settings.gradle`, so the artifact no longer depends on the checkout directory name.
4. **Java packages** `org.hivevm.cc.*` → **`org.hivevm.waggle.*`**, including the self-hosted
   grammars' `JAVA_PACKAGE`/`JAVA_IMPORTS` options and the `ServiceLoader` file
   `META-INF/services/org.hivevm.waggle.generator.Generator`. `org.hivevm.gradle`,
   `org.hivevm.core` and `org.hivevm.source` do not carry the brand and stay.
5. **Brand-carrying types:** `HiveCC` → **`Waggle`**, `HiveCCOptions` → **`WaggleOptions`**,
   `HiveCCVersion` → **`WaggleVersion`**; the tests follow (`CCParserTest` → `WaggleParserTest`,
   `HiveCCOptionsTest` → `WaggleOptionsTest`).
6. **Grammar file extension** `.jj` → **`.waggle`** for every grammar written in Waggle's syntax
   (the self-hosted grammars, test fixtures) and in the documentation. The sibling lexical file keeps
   `.lex`. `JavaGrammars/Java1.1.jj` keeps its name: it is a classic JavaCC grammar
   (`PARSER_BEGIN`), not a Waggle one.
   **The `.jjt` alias from ADR-0010 is removed.** The driver no longer special-cases any extension:
   the `.jjt` branch in `Parser` (which only printed a "Tree Builder" banner before reading the file
   unchanged), the never-true `.jjt` check in `ParserBuilder`, and `JJTreeParser` — the entry point
   of the dead JJTree pre-processor that only those two branches could reach — are deleted, and
   `JJTree.jjt` gives way to `JJTree.waggle`, the grammar the build already uses.
7. **Self-hosted grammar:** `JavaCC.jj` → **`Waggle.waggle`** (`grammar Waggle;`), `JJTree.jj` →
   `JJTree.waggle`.
8. **C++ runtime header:** `JavaCC.h` → **`Waggle.h`**, and the `JAVACC` prefix of its include guard,
   of every template include guard and of the configuration macros → **`WAGGLE`** (e.g.
   `JAVACC_CHAR_TYPE` → `WAGGLE_CHAR_TYPE`).
9. **Generated-file header and banner** read `Generated by HiveVM Waggle v.…` and
   `Waggle Version … (…)`.
10. **Repository** `hivevm/cc` → **`hivevm/waggle`**; `vcsUrl` and README badges point there.
11. **Bootstrap plugin.** `build.gradle` bootstraps with the published **`org.hivevm.waggle` 1.0.13**,
    the first release under the new id, instead of `org.hivevm.cc` 1.0.11.

Explicitly **out of scope** (unchanged):

- The **JavaCC heritage vocabulary**: `JJ*`/`jj*` identifiers in generator and generated code, the
  `JJPARSER_*`/`JJTREE_*` option keys, the C++ typedefs `JJChar`/`JJString`, and classes named after
  JavaCC or JJTree/JJDoc (`JavaCCErrors`, `JavaCCData`, `AbstractJavaCCParser`,
  `JavaCCParserDefault`, `JJDoc*`, `JJTree*`). They name the lineage (ADR-0003), not the product; a
  rename would churn every generated file for no user benefit. A later ADR may revisit them.
- **Accepted ADRs 0001–0013** keep saying "HiveVM CC" and `org.hivevm.cc`: they are historical
  record and are not edited. The one exception is mechanical: the two relative links from ADR-0004
  into `src/main/java/org/hivevm/cc/…` are repointed to the moved files so the documentation check
  (`scripts/check-docs.sh`) keeps passing; their link text and the decision are unchanged.
- The **version numbering** is not reset; the first release under the new id is 1.0.13.

## Consequences

- **Breaking for every consumer**, in one step: the plugin id, the Maven artifact, the Java packages
  (for `ParserBuilder` embedders), and — for the C++ target — the header name and the `JAVACC_*`
  macros that user code may define or test. Generated Java and Rust code is unaffected apart from its
  header comment, because neither emits the brand.
- Existing `.jj` grammars keep working (the extension is not checked); renaming them to `.waggle` is
  recommended, not required. A `.jjt` grammar also still generates — it is now read like any other
  grammar — but without the old "Tree Builder" banner; nothing else about its output changes.
- The rest of the JJTree pre-processor (`JJTreeParserDefault`, `JJTreeVisitor`, `TreeGenerator`,
  `ASTWriter`) stays dead code, as the README already records; removing it is separate work.
  *(Settled otherwise since: [ADR-0016](0016-tree-building-as-an-optional-module.md) decision 5 and
  [ADR-0019](0019-package-layout-and-dependency-dag.md) make `jjtree` the **tested reference
  consumer** of tree building — the build regenerates it from `JJTree.waggle` on every run and two
  tests exercise it, so it is not removed and it is not dead. This bullet records what was expected
  in September 2026, not what was decided.)*
- Consumers of `org.hivevm.cc` are stranded on the last `cc` release. The release notes of the first
  `waggle` release must state the migration (plugin id, packages, `Waggle.h`/`WAGGLE_*`).
- ADRs 0001–0013 use the old name; readers must know that "HiveVM CC" and "HiveVM Waggle" are the same
  project. The ADR index and this ADR make the link.
- Follow-up outside the repository: rename the GitHub repository, update the `origin` remote, and
  update www.hivevm.org.

## Alternatives considered

- **Rename only the product name, keep ids and packages.** Rejected: the old name would persist
  exactly where it is most visible to users (`plugins { id 'org.hivevm.cc' }`, imports), and every
  later attempt to finish the rename is a breaking change of its own.
- **Also rename the JavaCC heritage identifiers (`jj*`, `JJ*`, `JavaCC*`).** Rejected for now: several
  hundred occurrences, most of them in generated code, with no user-visible benefit and a large diff
  that would hide the actual rename. Can follow in its own ADR.
- **Keep `JavaCC.h`/`JAVACC_*` in the C++ runtime.** Rejected: the header file name and its macros are
  what a C++ user sees first; keeping JavaCC's name there while renaming everything else would be
  inconsistent, and this is the one breaking window where the change is cheap.
- **Publish a relocation/compatibility plugin under `org.hivevm.cc`** that forwards to Waggle.
  Rejected (YAGNI): it adds a second artifact to maintain; a clear release note is enough for the
  current user base. Can be added if a concrete consumer needs it.
